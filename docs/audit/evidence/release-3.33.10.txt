# Release evidence — v0.9.0-gui3.33.10

Tag: v0.9.0-gui3.33.10
Purpose: stop the hourly “1 file(s) uploaded” notification without disabling
completion notifications.

## Root cause

The planner emits an `Up` action for a directory that exists only on disk, but
`execute` deliberately skips it: the CLI creates a file's parent folders during
the upload. The health writer counted **every** `Up` action as an upload, so a
skipped directory incremented `uploaded` once per cycle.

On this machine one internal leftover directory existed only locally:

  ProtonDrive/.proton-debug-114515/   (contains only an empty
                                       .proton-sync-staging/)

It is skipped by `execute`, never recorded in state, and therefore replanned on
every cycle. The health snapshot showed the contradiction directly:

  actions: 1   uploaded: 1   local_entries: 1324   remote_entries: 1323

With a one-hour interval, the GUI saw a `syncing -> ok` transition with
`uploaded = 1` every hour and announced “1 file(s) uploaded” even though no
file was transferred.

## Fix

- `uploaded` now counts only `Action::Up` nodes that are files and did not fail,
  which is exactly the set `execute` transfers.
- This is not notification suppression: a real file upload still increments the
  counter and still notifies.
- Regression tests: a directory-only cycle counts 0, a real file counts 1, and
  a failed file is not counted.

## Runtime verification

Same engine state after installing 3.33.10:

  before: actions: 1   uploaded: 1   local_entries: 1324   remote_entries: 1323
  after:  actions: 1   uploaded: 0   local_entries: 1324   remote_entries: 1323

The skipped directory still appears in `actions`, so the condition that caused
the bug is present, but it no longer reports an upload.
